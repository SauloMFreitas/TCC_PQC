# Results

All values were produced on the machine described in the top-level README.
Column names are kept as emitted by the benchmark (Portuguese identifiers);
their meaning is given below.

## `timing/`

One directory per compiler configuration (`O0`, `O0_lto`, `O0_native`,
`O0_native_lto`, …, `O3_native_lto`). Times are in microseconds.
Statistics are computed over the measured iterations (warm-up excluded).

### `kem.csv`

| Column | Meaning |
|---|---|
| `algoritmo_nist` / `algoritmo_oqs` | NIST name / liboqs name |
| `nivel_nist` | NIST security level |
| `pk_bytes`, `sk_bytes`, `ct_bytes`, `ss_bytes` | public key, secret key, ciphertext, shared secret sizes |
| `{keygen,encaps,decaps}_{mean,stddev,min,median}_us` | timing statistics per operation |
| `memoria_kb` | change in allocated heap (`mallinfo2().uordblks`) across the measured loop, KB |

### `sig.csv`

Same as `kem.csv`, with `sig_max_bytes` (maximum signature size) and
`sig_real_bytes` (signature size actually produced for a 32-byte message),
and operations `keygen`, `sign`, `verify`.

### `sig_scale.csv`

`algoritmo_nist, nivel_nist, msg_bytes` followed by
`{sign,verify}_{mean,stddev,min,median}_us`, for 21 message sizes
(1 B to 1 MiB, powers of two).

### `*_all_flags.csv`

Concatenation of the per-configuration files with four leading columns:
`config`, `opt_level` (`O0`–`O3`), `march_native` (0/1), `lto` (0/1).
Regenerate with `python3 scripts/aggregate_results.py`.

## `memory/`

### `<config>/memory_results.csv` (stack painting)

| Column | Meaning |
|---|---|
| `algoritmo`, `operacao` | liboqs algorithm name, operation |
| `heap_delta_bytes` | net heap change across the operation (always 0) |
| `stack_bytes` | maximum stack depth used by the operation |
| `rss_before_kb`, `rss_after_kb`, `rss_delta_kb` | resident set size around the operation |
| `sucesso` | 1 if the operation succeeded |

### `<config>/massif_results_heap.csv` (Valgrind massif)

| Column | Meaning |
|---|---|
| `heap_peak_bytes`, `heap_peak_kb`, `heap_peak_mb` | peak useful heap during the operation |
| `total_peak_bytes`, `total_peak_kb` | peak of heap + allocator overhead + stacks (`mem_heap_B + mem_heap_extra_B + mem_stacks_B`) |

### Other files

| File | Content |
|---|---|
| `stack_O0_debug.csv` | stack table reported in the paper (reference `-O0 -g` build, NIST names in `algoritmo`, liboqs names in `nome_liboqs`) |
| `stack_rss_all_flags.csv`, `heap_peak_all_flags.csv` | per-config memory files concatenated (same leading columns as above) |
| `validation/flags_comparison.csv`, `validation/flags_summary.txt` | stack usage of each flag set relative to `-O0` |

## `logs/`

Console log of the run that produced `timing/`.

> **Note:** the CSVs in `timing/` were collected with 100 measured iterations
> and 20 warm-up iterations (see the log header). The harness now uses the
> 200/10 setting described in the paper; re-run `scripts/run_all.sh timing`
> to regenerate the data with it.

## Raw Valgrind output

The raw `.massif` files (≈2.6 GB for the 16 configurations) are not kept in
git. They are regenerated by `memory/run_memory_all_flags.sh` into
`memory/build_mem_<config>/massif_out/`.
